## Question

How expensive is the complete EXP-004 H2 protocol under the exact fixed-head
and FP16 branch-stack semantics, and is exact hidden-prefix reuse worth
implementing before the validation/test searches?

The benchmark reproduces the numerical model on which the canonical head was
trained: every DeBERTa block computes in FP32 and the complete hidden state is
rounded to FP16 before the next block. The new executor was bit-exact against
the original fragmented branch stack on canonical `[1..12]`, arbitrary
`[1,2,6,4,9]`, and repeated `[1,1,2]` paths (`max_abs_diff=0`).

## Prefix-reuse estimate

For the canonical length-12 parent, the configured action space contains 152
legal skip/repeat actions. If an unexplored action is selected uniformly and
all exact FP16 prefixes of the parent are retained, the generated child needs
an average of 7.467 newly evaluated blocks. Interpolation over the measured
means gives:

- GPU forward + fixed-head reward: 6.769 ms/simulation;
- conservative CPU action enumeration + maximum-branch UCB: 0.096 ms;
- combined: 6.865 ms/simulation;
- complete H2 protocol: **7.407 wall/GPU-hours** including startup.

Using a length-18 parent instead changes the estimate only modestly to 7.736
hours. The key benefit is avoiding the unchanged prefix, not assuming all
suffixes are only one to three layers long.

Exact-result cache hits were deliberately assumed to be zero in the main
estimate. Sensitivity is:

| Exact path-result cache hit rate | Estimated total hours |
|---:|---:|
| 0% | 7.41 |
| 10% | 6.68 |
| 25% | 5.59 |
| 50% | 3.76 |

## Runtime envelope and decision

| Execution assumption | Total hours |
|---|---:|
| Perfect same-path batch-64 grouping, unattained lower bound | 0.56 |
| Exact FP16 prefix cache, action-weighted length-12 parent | 7.41 |
| Exact FP16 prefix cache, action-weighted length-18 parent | 7.74 |
| No prefix reuse, full length-12 recomputation | 12.46 |
| No prefix reuse, full length-18 recomputation | 17.99 |

Exact prefix reuse lowers the relevant length-12 estimate from 12.46 to 7.41
hours, a **40.5% reduction**. This exceeds the project's earlier 30%
significance threshold. Therefore the H2 runner should implement a sample-local
GPU FP16 prefix-state dictionary before any full search. SSD/HDD caching is not
needed: one sample is searched at a time and even a conservative upper bound of
3,600 cached prefix states is small relative to 24 GiB for CLINC sequence
lengths.

Observed synchronization spikes and still-unimplemented orchestration justify
a 25% reserve: 7.407 × 1.25 = 9.26 hours. The operational allocation should be
rounded to **10 GPU-hours**, divided into independently resumable components.
This allocation is conservative without relying on exact-result cache hits or
an unimplemented cross-sample batch scheduler.

## Limitations

- The real parent path-length distribution is unknown until a validation-only
  pilot. Length-12 and length-18 action profiles bound the likely prefix-cache
  regime reasonably closely, but are not observed search distributions.
- The benchmark is a short engineering run rather than a multi-hour thermal
  soak. The 25% reserve covers the observed latency spikes and ordinary runner
  overhead, but power-state changes can still affect wall time.
- Batch-8/32/64 measurements are scheduler bounds only. The official estimate
  assumes sample-wise execution and does not claim those batching gains.
- This preflight establishes feasibility and numerical compatibility only. It
  says nothing about `R_short`, `R_recov`, or either H2 acceptance criterion.
